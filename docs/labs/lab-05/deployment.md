## 1. Stack and changes from the reference kit

| Part | What we use |
|---|---|
| App | React 18 client (Vite) + Express 4 API on Node 24, Prisma 5 ORM, PostgreSQL 17 |
| Container | One image from the root `Dockerfile`: client build, server build, then a slim Node 24 runtime that serves the API and the built client on port 3000 as the non-root `node` user |
| Compute | Cloud Run service `adviseslot` (scales to zero) |
| Database | Cloud SQL for PostgreSQL 17, connected through the Cloud SQL unix socket |
| Secrets | Secret Manager |
| Images | Artifact Registry |
| CI/CD | GitHub Actions: `ci-docker.yml` (job `test-and-docker`) on every PR into `sprint-1` and `main`; `deploy.yml` on every push to `main`, logging in to GCP with Workload Identity Federation (no key file) |

Changes from the Lab 5 starter kit (TokTickIT):

- Resource names use `adviseslot` instead of `toktickit`.
- PostgreSQL **17** instead of 16, the same major version as local development (D-25).
- No admin password: AdviseSlot has no admin account. Instead the seed needs `SEED_DEMO_PASSWORD` for its demo accounts; `deploy/deploy.sh` generates it into Secret Manager.
- The migrate job runs `npx prisma migrate deploy && npx prisma db seed`.
- `deploy/smoke_test.py` checks our API: `/api/ready` returns `"db": "up"`, the session is the `sid` cookie (not a bearer token), and `/api/slots/bookable` must answer 401 when logged out. It also checks that `/api/version` reports the commit just released.
- Extra: `deploy/setup-wif.sh` scripts the Workload Identity Federation setup that the kit describes in `docs/auto-deploy.md`, and `deploy/teardown.sh` also removes it.
- Extra: the page footer and `GET /api/version` show the running commit (#50).

## 2. Environment variables

No real value of a secret is in Git, the image, logs or the PDF. Local values come from `server/.env` (copied from `server/.env.example`, placeholders only) and are never committed.

### Application (server)

| Variable | Purpose | Secret? | Local value from | On Cloud Run from |
|---|---|---|---|---|
| `DATABASE_URL` | PostgreSQL connection string for Prisma | **Yes** | `server/.env` (local Docker database only) | Secret Manager `adviseslot-database-url`, mounted into the service and the migrate job. Generated by `deploy.sh`; uses the Cloud SQL socket `/cloudsql/adviseslot:asia-southeast1:adviseslot-pg` |
| `SEED_DEMO_PASSWORD` | Password the seed gives the demo accounts (12+ characters; the seed refuses to run without it) | **Yes** | `server/.env`, `server/.env.test` | Secret Manager `adviseslot-demo-password`, mounted into the **migrate job only**, not the service. Generated by `deploy.sh` |
| `NODE_ENV` | `production` turns on serving the built client and the `Secure` session cookie | No | `server/.env` (`development`), Dockerfile (`production`) | Set by `deploy.sh` (`production`) |
| `PORT` | Port Express listens on | No | `server/.env` (`3000`) | Dockerfile default `3000`; Cloud Run sends traffic to port 3000 |
| `CLIENT_ORIGIN` | Allowed CORS origin for the Vite dev server | No | `server/.env` (`http://localhost:5173`) | Not set: in production the client is served from the same origin, so CORS is not needed |
| `CLIENT_DIST` | Optional path of the built client | No | Not set | Not set; the default `/app/client/dist` in the image is used |
| `APP_COMMIT` | Commit SHA shown by `/api/version` and the footer | No (public, the repository is public) | Not set, so it shows `dev` | Set by `deploy/release.sh` to the released image tag (the commit SHA) |
| `TZ`, `APP_TIMEZONE` | Time zone `Asia/Bangkok`. The code formats times explicitly, so these do not change behaviour | No | `server/.env` | Set by `deploy.sh` |

### Client (build time)

| Variable | Purpose | Secret? | Value |
|---|---|---|---|
| `VITE_API_URL` | API address for local development | No (bundled into the browser code) | `client/.env` (`http://localhost:3000`). Not set for the Docker image: a production build calls the API on the same origin |

### First-time setup (already done, #42 and #44)

From the repository root in Cloud Shell, as a project Owner. Each script has a dry run that prints the commands and creates nothing; read it first.

```bash
DRY_RUN=1 PROJECT_ID=adviseslot bash deploy/deploy.sh
PROJECT_ID=adviseslot bash deploy/deploy.sh

DRY_RUN=1 PROJECT_ID=adviseslot bash deploy/setup-wif.sh
PROJECT_ID=adviseslot bash deploy/setup-wif.sh
```

Both are safe to re-run: what exists is reused, and credentials are never replaced. New service accounts and pools take a few minutes to become visible, so a first run may stop with "does not exist" or "permission denied"; wait and run the same script again. Read the demo password yourself with `gcloud secrets versions access latest --secret=adviseslot-demo-password` and never paste it anywhere.

### Cost control and teardown

Cloud SQL is billed per hour even when nobody uses the site (about ฿16 to 21 a day). Cloud Run scales to zero and costs almost nothing when idle. Stop the database when the site is not needed and start it before a demo or grading; the data is kept, and the site returns errors while it is stopped:

```bash
gcloud sql instances patch adviseslot-pg --activation-policy=NEVER --project adviseslot    # stop
gcloud sql instances patch adviseslot-pg --activation-policy=ALWAYS --project adviseslot   # start
```

Keep the service running until the instructor announces the end of grading. Then preview and run the teardown, which asks you to type the project ID, and check in the Console that nothing is left (SQL, Cloud Run services and jobs, Artifact Registry, Secret Manager):

```bash
DRY_RUN=1 PROJECT_ID=adviseslot bash deploy/teardown.sh
PROJECT_ID=adviseslot bash deploy/teardown.sh
```

## 4. Build, test, run, migrate and seed

Node 24 (`.nvmrc`) and Docker. The README has the full setup; these are the commands.

### Local development

```bash
docker compose up -d db                      # PostgreSQL 17 on host port 5433

cd server
cp .env.example .env && cp .env.test.example .env.test
npm install
npx prisma migrate dev                       # apply migrations to the dev database
npx prisma db seed                           # demo accounts and slots (safe to re-run)
npm run dev                                  # API on http://localhost:3000

cd ../client
cp .env.example .env
npm install
npm run dev                                  # UI on http://localhost:5173
```

The footer shows "AdviseSlot version dev" locally, because `APP_COMMIT` is not set.

### Tests

The same checks run in CI (`ci-docker.yml`, job `test-and-docker`) on every PR into `sprint-1` and `main`.

| Suite | Command | Needs |
|---|---|---|
| Server (Vitest, API and rules) | `cd server && npm test` | Database container; uses `adviseslot_test` from `server/.env.test` |
| Client build (type check + Vite) | `cd client && npm run build` | - |
| E2E journey (Playwright) | `cd e2e && npm install && npx playwright install chromium && npm test` | Database container and `server/.env.test`; starts its own API (3100) and client (5273) |
| Deploy scripts (offline) | `bash deploy/tests/test_release_stub.sh`<br>`bash deploy/tests/test_deploy_stub.sh`<br>`python3 -m unittest discover -s deploy/tests -p 'test_smoke.py'` | Nothing: fake `gcloud` and mocked HTTP, no GCP access |
| Docker image | `docker build -t adviseslot .` | Docker |

### Production container

```bash
docker compose --profile app up --build      # database + app image on http://localhost:3000
```

This builds the root `Dockerfile` (client and server builds, Node 24 slim, non-root), then runs
`prisma migrate deploy`, the seed and `node dist/index.js` with the placeholder values from
`server/.env.example`. The image itself only runs `node dist/index.js`; it never migrates or seeds
on start.

### Migrate and seed

| Where | How |
|---|---|
| Local dev database | `npx prisma migrate dev`, then `npx prisma db seed` (in `server/`) |
| Local test database | Automatic: the Vitest setup runs `prisma migrate deploy`; the Playwright setup runs it and the seed |
| Cloud SQL | The Cloud Run job `adviseslot-migrate` runs `npx prisma migrate deploy && npx prisma db seed` with the job's `DATABASE_URL` and `SEED_DEMO_PASSWORD` secrets (the service gets only `DATABASE_URL`). `deploy/release.sh` runs it on every release before the service is updated, and waits for it |

To run the Cloud SQL job by hand (for example after a manual database change):

```bash
gcloud run jobs execute adviseslot-migrate --wait --region asia-southeast1 --project adviseslot
```

The seed only adds what is missing. It never changes the password of an account that already
exists, so a new `adviseslot-demo-password` secret version does not change existing demo
logins.

## 5. Release procedure

### From Issue to production

1. **Issue** with label `lab5` (or the sprint's label) on the board.
2. **Branch** from `sprint-1`, commit, open a **PR into `sprint-1`** with the teammate as
   reviewer and link it to the Issue. CI (`test-and-docker`) must pass. The reviewer merges.
3. **Release PR** `sprint-1` -> `main`. The `protect-main` ruleset requires a PR, 1 approval,
   `test-and-docker` passing and the branch up to date with `main`, with no bypass. The reviewer
   merges.
4. The push to `main` starts **`deploy.yml`** (Actions > "Deploy demo"):
   1. runs `ci-docker.yml` again (`test-and-docker`); the deploy job waits for it to pass,
   2. logs in to GCP through Workload Identity Federation (GitHub environment `demo`, no key file),
   3. builds the image and pushes `adviseslot/adviseslot:<commit SHA>`,
   4. `deploy/release.sh`: pins the image by digest, runs the migrate job, updates the Cloud Run
      service with `APP_COMMIT=<commit SHA>` and gives the new revision 100% of traffic. A failed
      migration stops here and the old revision keeps serving,
   5. `deploy/smoke_test.py`: `/api/health`, `/api/ready`, the page, a 401 on a protected route,
      and `/api/version` must equal the released SHA,
   6. writes the image tag, digest and URL to the run summary.

Lab 5 release: Issue #50 -> PR #51 into `sprint-1` -> release PR #52 into `main` (merge commit
`715cfed`) -> deploy run 43258951754 -> revision `adviseslot-00003-tbf`.

### Find the running commit

Any of these shows the same SHA:

| Where | How |
|---|---|
| The site | Footer of every page: "AdviseSlot version `715cfed`" (hover for the full SHA) |
| API | `curl https://adviseslot-nfnam6jppq-as.a.run.app/api/version` -> `{"commit":"<full SHA>"}` |
| GitHub | Actions > "Deploy demo" > the run > Summary: image tag, digest and URL |
| Google Cloud | Cloud Run > `adviseslot` > Revisions: the serving revision's variable `APP_COMMIT` (the image is pinned by digest, `...adviseslot@sha256:...`; the `:<SHA>` tag is in Artifact Registry) |

### Roll back

Actions > "Deploy demo" > **Run workflow** on `main`, with `image_tag` = the full 40-character
SHA of an earlier release (its image is still in Artifact Registry). This skips the tests, the
build and the migration, points the service at that image and runs the smoke test. The footer
then shows the older SHA. To return, run it again with the newer SHA, or push a new release to
`main`.

A rollback does not undo database migrations, so only roll back across releases whose
migrations the older code can still run with.
